# BLKC v2 Specification

**Status:** Draft (2026-11-04)  
**Source:** `packages/core/src/index.ts`  
**Tests:** `packages/core/src/__tests__/schemas.test.ts`  
**Location:** `spec/v2.md` (moved from `docs/v2-spec.md` in Step 1)

This document is the executable specification for BLKC v2. The TypeScript schemas in the core package are the
source of truth, and the tests enforce the rules described here. Each test names the section it covers
(e.g. `describe("§3 attributes", ...)`).

---

## Overview

BLKC v1 described one thing: **backend AI/data modules (Blocks)** grouped into Kits and Circuits. v2 adds
the same vocabulary for **websites and trade bundles**: page sections, themes, default content, and Kanban
boards.

v2 adds this capability **without breaking any v1 manifest**. Every v1 Block parses unchanged as a
capability Block, via `parseAny()` (§10).

| Concept | v1 | v2 |
|---------|----|----|
| **Block** | Backend module | `kind: "ui"` page section **or** `kind: "capability"` module |
| **Kit** | List of Blocks | Template: Blocks + theme (`theme.json` shape) + default content |
| **Circuit** | List of Kits | Trade bundle: Kits + board templates + capability Blocks |
| **Logbook** | Hash-chained events | Same chain, shared across Sites, boards, MCP, and marketplace proof |

---

## §1 File names (D1)

Distinctive JSON file names, not new extensions. Editors, GitHub and humans already understand `.json`.

| File | Purpose |
|------|---------|
| `block.json` | Block manifest |
| `kit.json` | Kit manifest |
| `circuit.json` | Circuit manifest |
| `theme.json` | Theme definition (WordPress-compatible) |
| `pages/*.json` | Page templates |
| `boards/*.json` | Board templates |
| `logbook.jsonl` | Hash-chained audit trail |

`manifest.json` is accepted as an old name, with a deprecation warning (compatibility §17). `.jsonc` is
allowed for comments during development.

---

## §2 `$schema` (D2)

Every file declares `$schema` pointing at a stable address:

```
https://blkc.blackcode.space/schemas/v2/<kind>.json
```

Core generates the JSON Schema files at build time (zod 4's `z.toJSONSchema()`), ships them in the npm
package (`files`), and exports them at `@blkc-code/core/schemas/*`. The unpkg URL is the fallback when the
site is unreachable. Editors validate files against them with nothing to install.

---

## §3 The `attributes` map (D3)

One `attributes` map for UI Blocks. Each attribute declares its type, constraints, label and an optional
control. Built-in semantic types imply a default control. Core turns `attributes` into zod, JSON Schema and
TypeScript types via `compileAttributes()`. Authors never write zod or JSON Schema.

```json
"attributes": {
  "heading": { "type": "string", "required": true, "maxLength": 120, "label": "Heading" },
  "cta":     { "type": "link",  "label": "Button" },
  "image":   { "type": "image", "label": "Image" },
  "align":   { "type": "string", "enum": ["left", "center"], "default": "left",
               "control": "select", "label": "Alignment", "group": "style" }
}
```

Types: `string`, `number`, `boolean`, `richtext`, `link`, `image`, `color`, `list`. Each has a default
control. An attribute may override its control (`text`, `textarea`, `richtext`, `url`, `number`, `range`,
`toggle`, `select`, `color`, `image`, `link`, `repeater`).

## §4 Folder conventions (D4)

```
blocks/<id>/   block.json  [render.web.tsx]  [preview.png]  [README.md]
kits/<id>/     kit.json  theme.json  pages/*.json  [preview.png]
circuits/<id>/ circuit.json  boards/*.json
```

If `render.web.tsx` is present, the Block renders on web. `renderers` stays as an optional override. Three
levels of effort: just `block.json` (validates and gets listed), add a renderer (renders), add a preview and
README (looks finished).

---

## §5 Capability contracts as MCP tools (D5)

Capability Blocks describe each capability as an MCP tool: `name`, `description`, `input` and `output` schemas
in the attribute format (§3), `permissions`, and `run(input, ctx)`. `ctx` provides declared secrets, fetch
and a Logbook writer. A `permissions` field (`network`, `secrets: [...]`) declares what it needs. v1 is
TypeScript/JavaScript only; python/docker move to "later".

`blkc mcp describe <block>` prints the exact MCP `Tool` JSON. `blkc check` validates `input`/`output` as
JSON Schema and warns on short or vague descriptions.

---

## §6 Trust model (D6)

No runtime loading of unreviewed code. The pull request to `blkc-community/blocks` is where code gets
reviewed. `@blkc-code/render-web` bundles the approved Blocks when it is built; hosted Sites never load
community code at runtime. Self-hosters can use any Block. This mirrors WordPress core Blocks versus plugins.

---

## §7 Registry and `index.json` (D7, Q3, Q6)

On merge, each content repo's CI builds `index.json` (with `id`, `version`, `kind`, `tier`, `path`, `sha`,
`preview`), publishes it to GitHub Pages (`https://blkc-community.github.io/<repo>/index.json`), and appends
`*.publish` entries to `logbook.jsonl`. The catalog reads all three indexes. Nobody commits registry files.

Curation tiers (Q6): `community` (merged), `reviewed` (BCE security and accessibility review, allowed in
the Studio's Block picker), `bcm` (maintained by BCE). Stored as `tier` in `index.json`, never in the
item's own file.

---

## §8 Node tooling (D8)

The CLI runs on Node, bundled into one file. Commands: `blkc new block|kit|circuit <id>`, `blkc check`
(validates the whole repo), `blkc dev` (local preview with render-web), `blkc export` (project/html/zip/
static targets), `blkc mcp describe`. Content repos call the shared workflow
`uses: blkc-community/.github/.github/workflows/blkc-check.yml@main`.

---

## §9 The Logbook (D9)

The Logbook is infrastructure, not content: the `@blkc-code/logbook` package, a `logbook.jsonl` per repo,
and an optional `logbook` capability Block so Kits and Circuits can surface an audit trail. See §15.

---

## §10 Versioning (D10)

Each item has a semver version in its JSON file. References use semver ranges, resolved against the
generated indexes. Spec changes that break compatibility need a new `manifestVersion`.

D1–D5 ship as **0.2.0** of the packages. `manifestVersion: 2`. Version 1 manifests are accepted until an
end-of-support date set in `spec/support.md`, which defaults to 6 months after 0.2.0 ships. `parseAny()`
accepts v1 manifests and upgrades them in memory to v2, with warnings.

## §11 Block (shared fields)

All Blocks share these fields:

- `manifestVersion` (1 or 2, default 1)
- `id` (identifier: lowercase alphanumeric with hyphens, 3-64 chars)
- `name` (string)
- `summary` (string)
- `description` (string)
- `version` (string)
- `tags` (array of strings, default empty)
- `license` (string, default "MIT")
- `authors` (array of Person, default empty)
- `homepage` (URL, optional)
- `repository` (URL, optional)
- `docs` (URL, optional)
- `metrics` (array of UsageMetric, default empty)
- `visibility` ("public" or "private", default "public")
- `changelog` (array of ChangelogEntry, default empty)

### Capability Block (`kind: "capability"`)

Backend module. The v1 Block shape.

```json
{
  "kind": "capability",
  "entryPoint": "./index.js",
  "runtime": "bun",
  "sizeMB": 42,
  "inputs": ["prompt", "context"],
  "outputs": ["response"],
  "capabilities": [
    { "id": "generate-text", "description": "Generate text from prompts" }
  ]
}
```

Fields:
- `entryPoint` (string, required): path to the module's entry file
- `runtime` (enum: `"bun"` | `"node"` | `"python"` | `"docker"`, default `"bun"`): execution environment.
  **Note:** v2 narrows supported runtimes to TypeScript/JavaScript (§5); python/docker are "later".
- `sizeMB` (number, optional, 0-100): approximate memory usage
- `inputs` (array of strings, default empty): input parameter names
- `outputs` (array of strings, default empty): output parameter names
- `capabilities` (array of BlockCapability, default empty): named capabilities

**v2 addition — capability contract (D5):** `input` and `output` use the attribute format (§3); the code
exports `run(input, ctx)`. `ctx` provides declared secrets, fetch and a Logbook writer. `permissions` field
(`network`, `secrets: [...]`) declares what it needs.

**Reserved (format only, not implemented):**
- `runtime` may also be `"browser"` (default `"server"`). A browser capability Block runs client-side.
- A `models` / `assets` array (shape TBD) leaves room for model or large-asset declarations.
- A `game` metadata object (`xpCost`, `unlockCondition`, `icon`, `visualization`) leaves room for
  gamification without BLKC understanding game mechanics.

### UI Block (`kind: "ui"`)

A page section (hero, pricing, gallery, testimonials, etc.). It has these parts:

**1. Props schema.** Authors write props as a zod schema in the Block package, then emit JSON Schema:

```typescript
const HeroPropsSchema = z.object({
  heading: z.string(),
  subheading: z.string().optional(),
  cta: z.object({ label: z.string(), href: z.string().url() })
});
manifest.props = z.toJSONSchema(HeroPropsSchema, { io: "input" });
```

The `props` field must be a JSON Schema object schema with `properties`. Tests verify the manifest and zod
source haven't drifted.

**v2 (D3):** UI Blocks declare one `attributes` map (§3) instead of writing zod + JSON Schema + controls
separately. Core generates all three via `compileAttributes()`.

**2. Editor controls.** Modelled on WordPress `block.json`: `prop`, `control`, `group` (content/style/settings),
`label`, `help`, `placeholder`, `min`/`max`/`step`, `options` (for select), `fields` (for repeater).

Control types: `text`, `textarea`, `richtext`, `url`, `number`, `range`, `toggle`, `select`, `color`,
`image`, `link`, `repeater`.

**3. Block supports.** Mirrors WordPress `block.json` `supports`: `align`, `color` (text/background),
`spacing` (padding/margin), `typography` (fontSize/fontFamily). When supported, the editor offers Kit
theme presets instead of free values.

**4. Renderer reference.** Says which component draws the Block on each platform:

```json
{ "renderers": { "web": { "package": "@blkc-code/render-web", "export": "Hero", "version": "^0.1.0" } } }
```

Targets: `web`, `native`, `tv`, **and (reserved) `canvas`/`pixel`**. At least one renderer must be specified.

**5. Additional fields:** `category` (optional), `example` (sample props, must include every required prop).

## §12 Kit = Template

A Kit is a template composed of Blocks, optional theme, and optional default content. Fields: `blocks`
(array of KitBlockRef: `blockId`, `version`, `alias`, `required`, `config`), `theme` (Theme, optional),
`content` (KitContent with `pages`, each a `slug`/`title`/`blocks` list).

Validation: every `block` in a page's blocks must match the `blockId` or `alias` of one of the Kit's blocks.

---

## §13 Circuit = Trade Bundle

A Circuit is a vertical solution composed of Kits, board templates, and capability Blocks. Fields: `kits`
(array of CircuitKitRef), `boards` (array of BoardTemplate with `columns` and `transitions`), `capabilities`
(array of CircuitCapabilityRef).

Validation: every transition must reference real columns.

---

## §14 Theme

A subset of WordPress `theme.json` v3. Unknown keys are preserved. Validated parts: `settings.color.palette`,
`settings.color.gradients`, `settings.typography.fontFamilies`, `settings.typography.fontSizes`,
`settings.spacing.spacingSizes`, `settings.spacing.units`, `settings.layout`, `styles`. Renderers turn presets
into CSS custom properties (`--wp--preset--color--<slug>`).

---

## §15 Logbook = Shared Audit Trail

Hash-chained sequence of events. Entry fields: `id`, `timestamp`, `actor`, `event`, `subject` (optional),
`data`, `prevHash`, `hash`, `signature`, `proof`. Event namespaces: `site.revision`, `site.publish`,
`board.transition`, `mcp.write`, `market.proof`, `block.publish`, `kit.publish`, `circuit.publish`.

Chain integrity: each entry's hash is computed from the entry data excluding `hash`, `prevHash`, `signature`.
`prevHash` points to the previous entry's `hash`. Tamper-evident. Multi-tenant: one chain per tenant when
`subject.tenant` is set.

Verification: recompute each hash, verify `prevHash` chain, check signatures.

Platform-specific packages that render UI Blocks:

| Target | Package | Status |
|--------|---------|--------|
| Web | `@blkc-code/render-web` | In development |
| Native | `@blkc-code/render-native` | Planned |
| TV | `@blkc-code/render-tv` | Planned |
| Canvas/Pixel | `@blkc-code/render-canvas` | The `office` Block. Open to others through `registerCanvasBlock()`. |

static HTML export via `renderToHTML()`, accessibility WCAG 2.1 AA, bundle < 50KB gzipped.

## §17 Compatibility (v1 → v2)

1. `manifestVersion` is `1 | 2`, defaults to `1`. New manifests **must** declare `2`.
2. A Block with no `kind` is treated as a **capability** Block. Every v1 Block manifest parses unchanged.
3. `manifest.json` is accepted as an old file name (deprecation warning). New files use `block.json` etc.
4. Every new Kit and Circuit field is optional, or defaults to an empty list.
5. Logbook entries gain an optional `subject`. Omitted when absent, so existing entry hashes don't change.
6. Default license for Blocks remains `MIT`. Content (Blocks, Kits, Circuits) is MIT. Framework packages are
   Apache-2.0.
7. `repository` points at the item's folder in the shared content repo.
8. `parseAny()` accepts v1 manifests and upgrades them in memory to v2, with warnings.
9. Breaking changes wait for `manifestVersion: 3`.

## §19 Reserved format additions (gamification / AI)

Reserved now so the format does not need a breaking change later. Not implemented.

- `runtime` on capability Blocks: `"server"` (default) or `"browser"`. A browser capability Block runs
  client-side (e.g. Transformers.js embeddings).
- `models` / `assets` array on capability Blocks: leaves room for model or large-asset declarations.
- `game` metadata object on Blocks and Circuits: `xpCost`, `unlockCondition`, `icon`, `visualization`.
  Lets a game app read BLKC manifests and gamify them without BLKC understanding game mechanics.
- Block kinds stay `ui` / `capability`. No "game" kind. A game world is a Kit; an action is a capability
  Block.

Constraints recorded (future stories):
- Browser AI cannot use the single-HTML export (size limit + `file://` limits). Requires `static` or
  `project` target.
- Crawlers are server-only (CORS).
- Hosted sites require reviewed, pinned, licensed model files (D6, AS-8).
- "Zero server cost" is not accurate (download, device memory/battery, hosting model files are real costs).

AI/RAG implementation deferred to after Story 2.10. First PoC: server-side `docs-rag` Circuit on the
home site docs.

## §20 File format

- **Encoding**: UTF-8
- **Line endings**: LF (Unix-style)
- **Indentation**: 2 spaces
- **File extension**: `.json` (or `.jsonc` for comments during development)

### Example file structure

```
blocks/
  hero/
    block.json          # Block manifest
    render.web.tsx      # Renderer component (optional)
    preview.png         # Preview image (optional)
    README.md           # Documentation
kits/
  bakery-site/
    kit.json            # Kit manifest
    theme.json          # Theme definition
    pages/              # Page templates
      home.json
circuits/
  local-service/
    circuit.json        # Circuit manifest
    boards/             # Board templates
```

## §21 Validation

All manifests must parse against their schemas, follow the compatibility rules, and pass validation tests.
`blkc check` validates the whole repo and prints `BLKC-E*` codes.

---

## §22 Versioning

Semantic Versioning. Caret ranges (`^0.1.0`) for minor updates, exact versions (`0.1.0`) for exact match,
range expressions for complex constraints. Breaking changes need a new major version (NFR27).
